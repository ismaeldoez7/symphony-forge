# Review focus — FORGE-DELEG-1 delegation boundary

Spec: docs/specs/delegation-boundary.md
Plan: plans/active/FORGE-DELEG-1-briefed-bounded-measured-delegation-boundary.md
Decision: docs/decisions/0018-delegation-gates.md (proposed)

Three lenses in ONE pass: quality, performance, security.

Security matters most here:
- `factory/scripts/pre_tool_use.py` is a PreToolUse hook and must fail CLOSED.
  A command it cannot parse must never silently ALLOW a `--write` delegation,
  and an exception inside the hook must not become an implicit allow.
- A task id must never be able to build a filesystem path
  (`forge_cli/delegate.py: brief_path` / `SAFE_TASK_ID`).
- Launch authority, stage state, and locks live in protected Git control data;
  worker-writable `.factory` mirrors are best-effort and never trusted.
- `forge_cli/codex_status.py` parses third-party plugin JSON this repo does not
  own; it must be defensive and must never be able to fail a gate.

Quality:
- `forge_cli/stages.py::_measure` is the new completion gate. Look for ways a
  stage could still close on work it did not do, or be falsely refused.
- `dirty_at_start` subtraction: a path already dirty at start is excluded. Is
  the failure direction closed (refuse) rather than open (allow)?
- Required proof binds `{path}`, `{id}`, `{report}`, exact JUnit file identity,
  Git metadata, the protected task contract, protected authority, and one final
  product snapshot around the whole proof set.
- Tasks are strictly sequential inside one story worktree. Story dependencies,
  not task write scopes, determine which separate story worktrees may run in
  parallel.
- `unrunnable_reason` must not reject legitimate shell while still catching prose.

Deliberate, not findings:
- WORKFLOW_PATHS is narrower than pr_ready's EVIDENCE_PATHS on purpose
  (decision 0018 Consequences).
- `forge codex status` is advisory by design and always exits 0.
- decision 0018 is `proposed`: acceptance is human confirmation, not a code step.
- Delegation and proof commands are trusted repository inputs. The implementation
  signals a process group only while its captured leader identity is still live,
  then repeatedly discovers token-inheriting descendants through TERM/KILL and a
  post-exit quiet window. A child that deliberately replaces its environment to
  clear `FORGE_PROCESS_TOKEN` is outside this trusted-command boundary; hostile
  double-fork/environment-clearing containment is the separate digest-pinned
  container capability tracked as deferral D-0001.
- This is a local developer harness, not a process-fleet supervisor. Cleanup
  intentionally retains observed PID identities through one command so it fails
  closed against PID reuse; optimizing historical-PID pruning for builds that
  create thousands of processes is a non-blocking production-scale concern.
- Cross-UID child supervision is outside the local same-user harness boundary;
  launching and containing workers under other users requires the deferred
  privileged/container supervisor rather than broad host process inspection.
- Kernel-specific process handles (`pidfd`, macOS `libproc`) are intentionally
  outside this cross-platform local harness. The sub-second PID-reuse edge case
  is accepted for trusted commands and must not introduce platform ABI code;
  stronger identity belongs with the deferred container/supervisor boundary.
